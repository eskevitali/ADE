# Обновление ADE до 0.2.0 для совместного тестирования

Рабочий адрес: https://ade.vor-ort-service-rusz.at/dashboard.
Ветка тестирования: `codex/ade-0.2.0-engineering-releases`.
Эта версия — первый этап [плана реализации](IMPLEMENTATION_PLAN.md).

## До обновления

Выполнить из существующего каталога ADE на сервере. Сохранить текущий commit
(`git rev-parse HEAD`) и резервную копию `.env`, `projects/`, `governance/`,
`knowledge/`, `reviews/`, локального `data/`, если он существует, а также резервную
копию PostgreSQL. Архив с `.env` хранить вне Git с правами только владельца.
Не запускать `git clean`, `reset --hard`, удаление контейнеров или volumes.

Проверить `git status --short`: локальные изменения кода нужно сохранить до смены ветки.
Изменённые сгенерированные проекты не должны подменяться версиями из Git.
При конфликте переключения ветки остановиться и сохранить изменения, без принудительной перезаписи.

В `.env` задать (значения секретов придумать новые):

```dotenv
DOMAIN=ade.vor-ort-service-rusz.at
APP_ENV=production
ADMIN_USERNAME=имя_владельца
ADMIN_PASSWORD=новый_уникальный_пароль_не_короче_16_символов
SESSION_SECRET=новый_случайный_секрет_не_короче_32_символов
WORKSPACE_IMAGE=python:3.12-slim
SANDBOX_TIMEOUT=60
# Имя общей Docker-сети backend и ADI (проверьте docker inspect):
WORKSPACE_PROXY_NETWORK=ade-v4_default
```

Секрет можно сгенерировать: `python3 -c 'import secrets; print(secrets.token_urlsafe(48))'`.
Опубликованные раньше пароль и секрет больше использовать нельзя. После смены секрета
нужно войти заново. Значения ключей LLM и настройки существующих БД сохранить.
Для строгой воспроизводимости вместо тега `WORKSPACE_IMAGE` использовать digest
предварительно загруженного образа. Образ Python содержит стандартную библиотеку;
установка зависимостей генерируемого продукта в этой версии не реализована.

## Обновление кода

```bash
git fetch origin
git switch --track origin/codex/ade-0.2.0-engineering-releases
docker pull python:3.12-slim
docker compose build backend
docker compose up -d --no-deps backend
curl -fsS http://127.0.0.1:8000/health
```

Если ветка уже создана локально: `git switch codex/ade-0.2.0-engineering-releases`,
затем `git pull --ff-only`. `/health` должен показать `version: 0.2.0`.
При ошибке запуска: `docker compose logs --tail 80 backend`.
Ожидаемая причина отказа после обновления старой `.env` — не заменён опубликованный
секрет. Не присылать в чат `.env` или токены.

`web_network` и существующий reverse proxy сохраняются.
`WORKSPACE_PROXY_NETWORK` должен совпадать с существующей внутренней сетью backend.
Например, на сервере владельца это `ade_default`, а не `ade-v4_default`.
Compose передаёт значение из `.env`; после изменения пересоздайте backend. Для долгих проверок
reverse proxy должен допускать запрос не короче `SANDBOX_TIMEOUT + 30` секунд.
Python HTTP-приложение должно отвечать успешно на `/` и слушать `0.0.0.0:8000`.
Данные приложения монтируются в `/workspace/data`; контейнер работает с UID/GID 65534.
Если приложению нужна запись, владелец должен предоставить этому UID права на каталог
данных конкретного ADI. Исходники всегда доступны только для чтения.

## Проверки

На хосте с установленным uv:

```bash
./scripts/run_full_test.sh
./scripts/run_full_test.sh --run-docker
```

Тесты используют временные проекты, фиктивный тестовый вход и отключённые LLM-ключи;
не обращаются к рабочему dashboard. Docker-тесты создают временные контейнеры и сети.
Без `--run-docker` эти проверки пропускаются. Работа с реальной моделью проверяется
следующим пользовательским сценарием, а не выдаётся за результат unit-тестов.

1. Войти на dashboard новым паролем. Убедиться, что старые ADI и документы доступны.
2. Создать небольшой продукт на стандартной библиотеке Python с unittest-тестами
   или статическую HTML-страницу. Пройти существующие подтверждения требований и кода.
3. На странице проекта нажать **Проверить**. Проверить список проверок и диагностику.
4. Нажать **Проверить и развернуть**. Убедиться, что активный релиз появился и ссылка
   `/run/{id}/` открывает приложение. Отсутствие Docker, тестов или ошибка тестов
   должны блокировать запуск, сохраняя предыдущий релиз.
5. Сделать доработку и выпустить второй релиз. Проверить кнопку **Откатить релиз**.
   Откат возвращает код; содержимое данных не откатывается.
6. Проверить, что макет мобильного приложения остался превью, а не объявлен готовой сборкой.

Генерируемые страницы имеют браузерную sandbox-политику. Превью не имеют сетевых
прав, а `/run/{id}/` ограничен своим префиксом. Cookie/Authorization владельца не
передаются приложению, Set-Cookie приложения не изменяет сессию ADE. Для сложного
JavaScript-приложения с cookie-auth/CORS нужен отдельный домен исполнения — это
следующий этап, текущая версия не обещает такую совместимость.

## Инженерная память

`GET /api/knowledge/lessons` показывает кандидаты и утверждённый опыт.
`POST /api/knowledge/lessons` принимает `title`, `body`, `project_id`, `release_id`
существующего проверенного снимка; `POST /api/knowledge/lessons/{id}/approve`
утверждает урок от имени вошедшего владельца. До утверждения урок не используется
агентами. Утверждение не расширяет права и не переписывает правила автоматически.
Данные хранятся в `/app/data/engineering.sqlite3` (существующий volume backend_data).

## Возврат самой ADE

Переключиться на сохранённый до обновления commit или ветку, выполнить
`docker compose build backend` и `docker compose up -d --no-deps backend`.
Не удалять volumes. Новые секреты в `.env` сохранить. Дополнительные поля manifest
и каталоги releases старый код игнорирует. Старый код не соблюдает новые границы
проверок и безопасности; возврат предназначен для восстановления доступности.
